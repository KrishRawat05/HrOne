# Current Project Review

**Scope:** source and documentation inspection of the current repository. This is not a fresh test execution or a security audit. The historical defect catalogue below describes issues in the original starter implementation and records their intended fixes; it should not be read as a list of defects still present.

## Summary

The current implementation follows the documented API shape across employee management, punch-in/out, regularization, attendance listing, analytics, and explain routes. It centralizes UTC/epoch conversion and attendance calculations, uses database constraints for duplicate-write protection, paginates attendance in MongoDB, and includes integration tests for many boundary and concurrency cases.

## Findings and Risks

| Severity | Finding | Impact / recommended action |
|---|---|---|
| High | No authentication or authorization is implemented. `regularized_by` is caller-supplied text, and admin explain routes are public. | Do not expose this API to untrusted networks. Add identity, role checks, and operational access controls before production use. |
| Medium | Department trend calculates daily headcount in Python by scanning all department employees for each date. | Cost grows with department size and date range. For larger datasets, move headcount calculation into a MongoDB aggregation or precomputed daily summary. |
| Medium | Test fixture targets `mongodb://localhost:27017` directly. | `MONGO_URI` does not redirect integration tests. Provide a local MongoDB or change the fixture when running against a container/CI service on another URI. |
| Medium | `sample_seed.py` deletes all documents in both configured collections before loading fixtures; `seed_100k.py --drop` drops its target collections. | Use a disposable database for seed workflows and make the target explicit before running either script. |
| Low | `verify_explain.py` imports `requests`, which is not in `requirements.txt`. | Install `requests` separately when using the optional verifier, or declare it as a development dependency. |
| Low | Synchronous PyMongo and no holiday calendar are intentional implementation constraints. | Load-test the chosen Uvicorn worker/thread configuration. Treat working days as Monday-Friday only unless a holiday source is added. |
| Low | The trend route requires MongoDB aggregation support for `$densify` and `$fill`. | Keep the server version aligned with the documented minimum (MongoDB 6.0+) and exercise analytics against the deployment version. |

## Index Count Correction

Startup creates **seven** application indexes: three on `employees` and four on `attendance_logs`, in addition to MongoDB's default `_id` indexes. `DECISIONS.md` and the README now use this count.

## Verification Notes

The checked-in test suite uses a real MongoDB service and covers key validation, business-rule boundaries, concurrency behavior, and analytics. Tests were not executed as part of this documentation update. For the exact local setup, commands, and known caveats, see [README.md](README.md) and [BUILD_GUIDE.md](BUILD_GUIDE.md).

# Historical Defect Catalogue: Starter `app/main.py`

This section is retained as implementation history. It was reviewed against `openapi.yaml` (the contract), `DATA_MODEL.md`, and business rules R1-R10.
Each row states the original location, what the code did wrong, a concrete failing input or
symptom, and what the fix is.  Numbers in "Fixed at" refer to the rewritten `app/main.py`.

---

## Defects

| # | Where (function / line) | What is wrong | How you'd notice it (test / input / symptom) | How it was fixed |
|---|---|---|---|---|
| D1 | `health()` | Always returns `{"status":"ok"}` — no MongoDB ping. Never returns 503. | Stop MongoDB and `GET /health` → still gets 200. The runner polls `/health` before testing; it would never discover Mongo is down. | Added `client.admin.command("ping")` inside a try/except; return 503 on any exception. |
| D2 | `create_employee()` | Check-then-insert race: `find_one` then `insert_one` are two separate operations. Two concurrent identical requests both pass the `find_one` check, then both insert, creating a duplicate. | Hammer `POST /employees` with the same `emp_code` from two threads simultaneously → both return 201. | Removed the `find_one` check entirely. Rely on the unique index (D3) and catch `DuplicateKeyError` → 409. |
| D3 | startup (missing) | No indexes are created anywhere. Without a unique index on `emp_code`, `DuplicateKeyError` can never fire for D2. The `(emp_code, date)` compound index does not exist either, so the punch-in race guard (D19) and all filtered list queries run COLLSCAN. | `GET /admin/explain/attendance_list` → plan shows `COLLSCAN`. Concurrent identical punch-ins both succeed. | Added a `lifespan` handler that calls `create_index` for `employees.emp_code` (unique) and `attendance_logs.(emp_code, date)` (unique) and `attendance_logs.(date desc, emp_code asc)` at startup. |
| D4 | `create_employee()` line: `doc["created_at"] = datetime.now()` | `datetime.now()` returns a **naive local-time** datetime. On any server whose timezone is not UTC this stores a wrong BSON date. | On a UTC+05:30 server, a record created at 09:00 IST is stored as `04:30 UTC` — but only because the system clock happens to be IST; on a UTC server it would be stored 5:30 h early. | Changed to `datetime.now(UTC)` (timezone-aware UTC). |
| D5 | `create_employee()` last three lines | `insert_one(doc)` mutates `doc` in place, adding `_id`. The code then calls `doc.pop("_id", None)` **after** using `doc` to build the return value — so `_id` is still in the dict that is serialised and sent to the client. | `POST /employees` → response body contains `"_id": "..."`. | Replaced the entire serialisation with `_fmt_employee(doc)` which builds a new dict with only the allowed fields. |
| D6 | `create_employee()` | `created_at` is returned as a raw Python `datetime` object. FastAPI serialises it as an ISO string (`"2026-01-05T04:30:00"`), not the required epoch milliseconds integer. | `POST /employees` → `created_at` is `"2026-01-05T04:30:00"` not `1783312500000`. | `_fmt_employee()` converts `created_at` via `dt_to_ms()`. |
| D7 | `EmployeeIn` model | No field validation. `emp_code` accepts any string (e.g. `"foo"`). Email, shift times, `joined_on`, name/department lengths — all unchecked. `shift_start == shift_end` is accepted. | `POST /employees {"emp_code":"BAD","email":"not-an-email",...}` → 201. | Added `@field_validator` for every field and a `@model_validator` that rejects `shift_start == shift_end`. |
| D8 | `list_employees()` line: `skip = page * page_size` | Off-by-one: page 1 skips `1 × page_size` rows (the first page), page 2 skips `2 × page_size`, etc. Nothing is ever returned for page 1. | `GET /employees?page=1` → items is empty even when employees exist. | Changed to `skip = (page - 1) * page_size`. |
| D9 | `list_employees()` line: `total = db.employees.count_documents({})` | `total` always counts **all** employees, ignoring the `department` filter. A filter for `"Engineering"` (3 employees) would return `total=6`. | `GET /employees?department=Engineering` → `total` is the total count of all employees. | Changed to `employees_col.count_documents(q)` where `q` is the same filter object. |
| D10 | `list_employees()` | No `.sort()` on the cursor. Documents are returned in MongoDB natural order (insertion order), not by `emp_code` ascending as required. | With employees inserted out-of-order, `GET /employees` returns them in insertion order. | Added `.sort("emp_code", ASCENDING)` to the cursor. |
| D11 | `list_employees()` | `created_at` is a `datetime` object in the MongoDB document; the `{"_id":0}` projection returns it as-is and FastAPI serialises it as a string. | `GET /employees` → `created_at` is `"2026-01-05T04:30:00"` not an integer. | `_fmt_employee()` converts it to epoch ms. |
| D12 | `list_employees()` params | `page_size` has no maximum; a client can request `page_size=1000000` and dump the whole collection. `page` has no minimum, allowing `page=0` which returns the wrong slice. | `GET /employees?page_size=999999` → full collection scan. | Added `Query(ge=1)` for page and `Query(ge=1, le=100)` for page_size; FastAPI returns 422 automatically. |
| D13 | `punch_in()` | `emp = db.employees.find_one(...)` result is never checked for `None`. The very next use is `emp["shift_start"]`, which raises `TypeError: 'NoneType' object is not subscriptable` when the employee does not exist — giving a 500, not a 404. | `POST /attendance/punch-in {"emp_code":"EMP9999",...}` → 500. | Added `if emp is None: raise HTTPException(404, ...)` immediately after the lookup. |
| D14 | `punch_in()` line: `datetime.fromtimestamp(body.punched_at / 1000)` | `fromtimestamp` uses the **local system timezone** by default. On a non-UTC host the stored BSON date is wrong. | On a UTC+05:30 server a punch-in at epoch 1783312500000 is stored 5.5 h ahead of the correct UTC value. | Changed to `ms_to_dt()` which calls `datetime.fromtimestamp(seconds, tz=UTC)`. |
| D15 | `punch_in()` line: `d = ts.date().isoformat()` | `ts.date()` returns the **local** calendar date of the datetime. If the server is not in IST, or if the punch crosses midnight in IST, the attendance date is wrong. | An employee punches in at 00:15 IST (18:45 UTC the previous day) → the stored date is one day early. | Replaced with `compute_attendance_date(ts_utc, emp["shift_start"], emp["shift_end"])` which converts to IST first. |
| D16 | `punch_in()` | R1 overnight shift rule not implemented. For a 22:00-06:00 shift, a punch-in at 05:30 IST should produce the attendance date of the **previous** day. | `POST /attendance/punch-in` for EMP0005 (22:00-06:00) at 05:30 IST → date stored is today, not yesterday. | `compute_attendance_date()` detects `shift_end <= shift_start` and subtracts one day when the punch time is before `shift_end`. |
| D17 | `PunchInIn` model / `punch_in()` | No epoch-ms validation. Floats (`1783312500.0`), strings (`"now"`), and seconds-scale integers (`1783312` — below `1e11`) are all silently accepted. | `POST /attendance/punch-in {"emp_code":"EMP0001","punched_at":1783312}` → 201 with a date in 1970. | `_validate_epoch_ms()` rejects non-int, bool, float, and values outside `[1e11, 4.1e12]`; called from `PunchInIn.validate_punched_at`. |
| D18 | `punch_in()` and all helpers | No truncation to whole seconds before any calculation (R1). Sub-second precision in `punched_at` affects `late_minutes`, `work_hours`, etc. | Punch-in at `09:40:00.900` should count as `09:40:00` for late calculation → should give 0; without truncation it gives 0 only by chance. | `ms_to_dt()` does integer division `ms // 1000` before `fromtimestamp`, discarding any sub-second part. |
| D19 | `punch_in()` | Check-then-insert race identical to D2. `find_one` + `insert_one` are separate operations; two simultaneous requests for the same `(emp_code, date)` can both insert. | Two threads `POST /attendance/punch-in` for the same employee at the same instant → both get 201 and two records are created. | Removed the `find_one` check. The unique index on `(emp_code, date)` (D3) means the second insert raises `DuplicateKeyError` → 409. |
| D20 | `punch_in()` last lines | `_id` is exposed in the response under the key `"id"`. `_id` must never appear in any response. | `POST /attendance/punch-in` → response body contains `"id": "68a1..."`. | Replaced ad-hoc serialisation with `_fmt_record()`, which builds the response from named fields only. |
| D21 | `PunchInIn` model | `status` accepts any string. `ABSENT` and `LEAVE` must be rejected at punch-in (openapi.yaml PunchInRequest uses `PresenceStatus`). | `POST /attendance/punch-in {"status":"ABSENT",...}` → 201. | Added `@field_validator("status")` that permits only `PRESENT`, `WFH`, `ON_DUTY`. |
| D22 | `punch_in()` | `datetime.fromtimestamp(ms/1000)` (no `tz` arg) produces a **naive** datetime. PyMongo stores it as a BSON date assuming local time, not UTC. All subsequent comparisons and aggregations use the wrong instant. | A punch-in stored on a UTC+05:30 server is 5.5 h ahead of the intended UTC time. | `ms_to_dt()` passes `tz=UTC`, producing an aware UTC datetime. The MongoDB client is also opened with `tz_aware=True, tzinfo=UTC`. |
| D23 | `compute_late_minutes()` | Grace threshold check is `minutes > 10` (integer minutes), losing sub-minute precision. At exactly 10:00 the employee IS in grace; at 10:00:01 they are late. `600 // 60 = 10` and `10 > 10` is `False`, so 10:01 incorrectly shows 0. The spec example says `09:40:01 → 10`. | Punch-in at 09:40:01 (601 s after 09:30) → returns 0 instead of 10. | Threshold changed to `diff_seconds <= 600`; `diff_seconds` is the integer seconds since shift_start. |
| D24 | `compute_late_minutes()` line: `start = punch_in.replace(hour=h, minute=m, ...)` | `.replace()` on a timezone-aware datetime keeps the same tzinfo, but the `hour`/`minute` here are **IST hours**, not UTC hours. For a 09:30 IST shift, `replace(hour=9, minute=30)` on a UTC datetime builds `09:30 UTC` — 5.5 h too early — producing a wildly wrong `late_minutes`. | Punch-in at 09:40 IST (04:10 UTC). `replace(hour=9,minute=30)` gives `09:30 UTC`. Diff = `04:10 − 09:30` = −5h20m → negative → 0. Late employee appears on-time. | `_shift_start_dt()` converts `punch_in_utc` to IST, builds the shift-start in IST, then converts back to UTC for comparison. |
| D25 | `compute_work_hours()` | Uses Python's built-in `round()`, which applies IEEE-754 half-to-even (banker's rounding): `round(2.5) = 2`, `round(3.5) = 4`. R4 requires half-up rounding. | `work_hours` for a session of exactly 2.5 h → `round(2.5, 2) = 2.5` coincidentally correct, but `(seconds/3600)` that lands exactly on `.5` at 2 decimal places rounds the wrong way half the time. | Changed to `Decimal(...).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`. |
| D26 | `compute_overtime()` | No 30-minute minimum. R3: `overtime_minutes` is 0 unless the employee stayed ≥ 30 minutes past shift end. The starter returns any positive value. | Employee leaves 5 minutes after shift end → starter returns 5, spec requires 0. | Added `if diff_seconds < 30 * 60: return 0`. |
| D27 | `compute_overtime()` | `datetime.fromisoformat(date_str)` produces a **naive** date. `.replace(tzinfo=IST)` then makes it IST-aware. `punch_out` in the original code was a naive local-time datetime (D22). Comparing naive with aware raises `TypeError`. | Any call to `punch_out` endpoint → `TypeError: can't subtract offset-naive and offset-aware datetimes` → 500. | Rewritten as `compute_overtime_minutes_from_shift_end(punch_out_utc, shift_end_utc)` that receives two UTC-aware datetimes; shift_end_utc is built in the caller with `tzinfo=IST` then converted. |
| D28 | `compute_overtime()` | No truncation to whole seconds before the overtime calculation (R1). | Sub-second part of `punch_out` affects the overtime boundary comparison. | `ms_to_dt()` truncates at the boundary; both `punch_in_utc` and `punch_out_utc` are whole-second datetimes by the time they reach any helper. |
| D29 | `list_attendance()` | `list(db.attendance_logs.find(q))` loads the **entire filtered result set into memory**, then sorts and paginates in Python. On 100 000 records this is a full COLLSCAN + OOM risk. | `GET /attendance` on a 100k collection → multi-second response, high memory usage; `/admin/explain/attendance_list` shows COLLSCAN. | Removed the in-memory fetch. Added `.sort().skip().limit()` directly on the cursor; `count_documents(q)` gives the total without fetching documents. |
| D30 | `list_attendance()` | `total = len(docs)` was the count of the **in-memory filtered list** — correct as a count, but only because the entire filtered set was fetched. Once D29 is fixed (cursor-based pagination), total must come from `count_documents`. The existing code also happened to ignore the off-by-one from D8 because it sliced the already-in-memory list. | (Secondary consequence of D29.) | `total = attendance_col.count_documents(q)`. |
| D31 | `list_attendance()` | `d["id"] = str(d.pop("_id"))` exposes `_id` under the key `"id"`. The contract says `_id` never appears in any response. | `GET /attendance` → each item has `"id": "68a1..."`. | Replaced with `_fmt_record(doc)` applied to each cursor result; `{"_id":0}` projection also added to the find. |
| D32 | `list_attendance()` | `punch_in` and `punch_out` are `datetime` objects inside the documents returned from MongoDB; they are serialised by FastAPI as ISO strings, not epoch milliseconds. | `GET /attendance` → `punch_in` is `"2026-07-06T03:58:00"` instead of `1751774280000`. | `_fmt_record()` converts all `datetime` fields to epoch ms via `dt_to_ms()`. |
| D33 | `list_attendance()` | No validation that `date_from <= date_to`. Sending `date_from > date_to` returns an empty but 200 result; the contract requires 422. | `GET /attendance?date_from=2026-07-10&date_to=2026-07-01` → 200 with empty items. | Added an explicit check and `raise HTTPException(422, ...)`. |
| D34 | `list_attendance()` | Sort happens in Python (`docs.sort(key=lambda d: d["date"], reverse=True)`) after fetching all documents. The secondary sort key (`emp_code` ascending) is absent entirely. | When two records share a date, their order within that date is non-deterministic. Pagination is also inconsistent across pages because the order is resolved after fetching. | Moved sort to MongoDB cursor: `.sort([("date", DESCENDING), ("emp_code", ASCENDING)])`. |
| D35 | `list_attendance()` params | `page_size` has no maximum and `page` has no minimum (same issue as D12 but for the attendance list). | `GET /attendance?page_size=500000` → full collection scan delivered in one response. | Added `Query(ge=1)` and `Query(ge=1, le=100)` on the parameters. |
| D36 | startup (missing) | No indexes created anywhere — see D3 for the full list.  Also there was no `lifespan` or `@app.on_event("startup")` hook at all. | Cold-start then `GET /admin/explain/attendance_list` → COLLSCAN. | `lifespan` async context manager creates all indexes idempotently. |
| D37 | module level: `MongoClient(os.getenv("MONGO_URI", "mongodb://localhost:27017"))` | Hard-coded fallback URI. The brief says "read from real environment variables; never hard-code". If `MONGO_URI` is unset the app silently connects to localhost instead of failing clearly. | Start without `MONGO_URI` set → app starts, connects to localhost (or silently fails in production). | Changed to `os.environ["MONGO_URI"]` (no default). A missing var raises `KeyError` at import time with a clear message. Same for `MONGO_DB`. |
| D38 | file (missing endpoints) | `POST /attendance/punch-out`, `PATCH /attendance/{emp_code}/{date}`, `GET /analytics/employees/{emp_code}/monthly`, `GET /analytics/departments/summary`, `GET /analytics/leaderboard/late`, `GET /analytics/departments/{department}/trend`, and `GET /admin/explain/{endpoint}` are entirely absent. | Any call to the above returns 404 from FastAPI's router (not a business-logic 404). | All seven endpoints implemented. |

## Things examined and found NOT to be defects

| What | Why it's fine |
|---|---|
| `IST = timezone(timedelta(hours=5, minutes=30))` | Correct UTC+05:30. No defect. |
| `load_dotenv()` called before `os.getenv()` | Correct order: `.env` is loaded first, but real env vars (already in `os.environ`) are not overwritten because `python-dotenv` defaults to `override=False`. |
| `FastAPI(title=..., version="2.0.0")` | Matches `openapi.yaml` info block. |
| Using synchronous `pymongo` (not `motor`) | The brief allows PyMongo; the server is thread-per-request via Uvicorn workers. Fine. |
| Pydantic `BaseModel` for request bodies | Correct pattern; FastAPI returns 422 automatically for type mismatches. |
| Returning `{"items":..., "total":..., "page":..., "page_size":...}` | Matches `EmployeePage` and `AttendancePage` schemas. |
